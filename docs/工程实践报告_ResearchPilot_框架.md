## 3.2 项目背景与需求分析

> 【写作提示】范例 3.2 采用"国家政策背景 → 领域问题 → 本研究切入点"的论述链。本节对应改为：科研领域的普遍痛点 → 现有工具/方法不足 → 本项目要解决的问题与意义。

### 3.2.1 背景：科研文献调研与论文研读的痛点

科学研究日益依赖对海量文献的高效调研与深度阅读，但当前存在三类突出问题：其一，文献数量快速增长，检索结果动辄数百上千条，筛选"真正相关"论文耗时巨大；其二，论文核心信息大量蕴含于图表之中，仅做全文文本检索难以定位到具体证据；其三，综述或研究过程中引用的结论常常"出处不明"，缺乏可回溯的页码、区域与原文依据，容易产生引用失真甚至幻觉。

### 3.2.2 现有方法与工具不足

通用大模型问答（ChatGPT 类）存在联网与幻觉风险，不适合直接用于严谨文献综述；现有文献管理工具（如 Zotero、EndNote）主要解决"收藏与管理"，不具备自动检索策略生成与证据化深读能力；云端学术助手虽提供搜索与总结，但需要上传论文全文，存在隐私顾虑，且对本地视觉模型与"证据可追溯"的支持有限。

### 3.2.3 本项目目标与意义

针对上述问题，本项目提出并实现一个本地优先、证据可追溯的多模态论文研究助手。其意义在于：（1）将"课题描述 → 检索词与检索策略生成 → 文献检索 → 论文筛选"的繁琐过程交由大模型 + MCP 工具自动完成，显著降低调研门槛；（2）对 PDF 正文与图表进行多模态解析，使"图里的信息"也能被检索、阅读与分析；（3）所有结论绑定证据来源（页码、区域、原文/裁剪图、哈希），支持确认/存疑/排除复核，为严肃科研提供可审计的分析结果；（4）全程本地运行，论文全文不出本机，保障数据隐私。

## 3.3 总体方案设计

### 3.3.1 设计原则

> 【写作提示】说明本项目遵循的工程约束，体现专业性（可参考范例 3.4 技术路线段落的写法，先总述再分述）。

项目遵循如下设计原则：（1）本地优先：模型推理、全文解析全部在本地完成，不依赖云服务；（2）边界清晰：所有外部学术数据源（OpenAlex、Crossref、arXiv）与文件解析能力封装在 MCP/Provider 边界之后，业务节点不直接依赖第三方协议；（3）证据可追溯：文本、视觉、表格三类证据均记录来源页码、区域坐标、原文/裁剪图与 SHA-256 来源哈希；（4）任务可恢复：基于 SQLite 持久化后台任务与 LangGraph Checkpoint，服务重启后可继续未完成任务；（5）未确认不分析：未确认论文前不下载或分析全文，避免隐私与资源浪费。

### 3.3.2 用户流程与系统架构

系统以 Streamlit 工作台为用户入口，工作流程分为四步：

1. 描述课题：填写研究问题、当前方案、主要困难与目标指标；
2. 检索文献：大模型理解课题并生成检索词与检索策略，MCP 工具从 OpenAlex、Crossref、arXiv 多源并发检索、规范化、去重并按相关度排序；
3. 选择论文：查看检索策略、摘要与相关性说明，选择一至两篇并补充分析要求；
4. 证据化分析：自动获取所选论文全文（失败时可上传 PDF），依次完成逐篇证据化分析、图表证据提取、双篇比较，最终进行证据复核（确认/存疑/排除）并保存到项目。

后端采用 FastAPI 提供统一 REST API（共 8 种路径、10 个操作），覆盖健康检查、项目增删改查、统一工作台读模型、动作执行（运行/重试/重新检索/重新选择/证据复核）、PDF 上传与分析、证据与裁剪图资源读取。LangGraph 负责研究工作流编排与状态管理，内部按 Repository（数据访问）、Service（业务逻辑）、Worker（后台任务）与 MCP 工具（外部能力）分层组织。

## 3.5 关键模块设计与实现

> 【写作提示】本节对应范例 3.6"工程实践操作"，是全篇核心，范例按"指标体系构建→分模块计算→综合"组织，每小节给出公式、处理流程截图与结果图。本项目改为按功能模块展开：每个小节 = 功能目标 → 设计思路 → 关键实现（贴关键代码/界面截图）→ 效果。下面的预填内容请对照你的实际分工增删。

### 3.5.1 检索策略生成与多源文献检索

本模块解决"检索词与检索策略从哪来"的问题。设计上先由大模型理解课题，输出规范化的目标、主题词、时间范围与检索策略（结构化 Schema 校验），再由 Literature MCP 调用 OpenAlex、Crossref、arXiv 三个数据源并发检索，返回结果统一规范化后合并、去重。去重基于标题与 DOI 相似度，排序采用两阶段策略：先按元数据相关性粗排，再由模型结合摘要做语义精排，兼顾效率与准确率。部分来源失败时其余来源正常返回，实现容错。

### 3.5.2 论文全文获取与 PDF 多模态解析

用户确认论文后，系统按元数据提供的链接自动获取 PDF；获取失败时支持上传。解析层基于 PyMuPDF 实现：优先抽取原生文本层；对扫描型页面按需触发 OCR；同时对页面中的位图与矢量区域进行识别与稳定裁剪，输出可用于视觉模型分析的图片证据；表格内容以结构化形式提取。解析产物统一落入项目工作区，便于追溯。

### 3.5.3 本地视觉模型图表证据分析

针对"图里的信息难以检索与理解"的问题，模块将裁剪得到的图表区域送入本地视觉模型，由模型输出图表类型、内容描述与对研究结论的支撑说明，并经 Pydantic Schema 校验保证结构稳定。该能力覆盖架构图、结果图、消融图与扫描页面等常见学术图表类型，使最终分析不仅引用文字，还能引用图内证据。

### 3.5.4 证据溯源、双篇比较与证据复核

所有文本、视觉与表格证据均记录来源页码、页面区域、原文/裁剪图与 SHA-256 来源哈希，保证"每个结论都可回到原文献的某一页某一区域"。选定两篇论文时，系统额外生成共同点、差异、互补性与适用条件的双篇比较。证据复核环节允许用户将证据标记为确认、存疑或排除，复核结果随项目持久化保存，为后续综述写作提供可信底稿。系统只呈现证据、差异、冲突与风险，不自动宣称研究方向具有创新性。

## 3.7 结果与分析

> 【写作提示】范例 3.7 先给"时间上/空间上"的分析结论，再以文献与政策佐证结论（3.7.1），最后列实践关键问题（3.7.2）。本节对应给出：系统达到的效果与证据 → 与同类工具的对比/验证 → 存在的不足。

### 3.7.1 实践结果

从功能闭环看，系统完成了从课题描述到证据化分析的全流程贯通：输入研究问题后，系统可自动生成检索策略并完成多源检索、去重与排序；选定论文后可自动获取全文，完成含图表的证据化分析，输出逐篇结论与双篇比较；证据复核结果可持久化复用。端到端演示（RGB-LWIR 配准与融合课题）输出完整、可复现。从工程质量看，自动化测试与规范检查全部通过，服务重启恢复、故障容错等可靠性目标经审计验证达到预期。量化层面，端到端回归评测 20 项任务全部通过（冻结快照综合得分 0.99），文献相关性金标准上 Precision、Recall、F1 均为 1.0，全量自动化测试 77 项通过，详见 3.6.1。

### 3.7.2 结论与验证

为保证结论的可靠性，系统在多处设计上做了验证性约束：检索结果的规范化与去重、证据的页码与哈希溯源、视觉模型输出的 Schema 校验、复核机制的人工确认环节，均使"模型说什么"与"文献里有什么"能够相互对证。与同类云端学术助手相比，本系统在证据可追溯性与数据隐私上有明显优势；局限在于对本地模型能力依赖较高，图表理解的准确率受视觉模型制约。

### 3.7.3 实践关键问题与不足

> 【写作提示】范例 3.7.2 按"问题—原因—影响"句式列举数条不足。以下条款已依据项目问题记录（docs/KNOWN_ISSUES.md）起草，请对照你的真实实践经历核对、补充或调整后定稿。

（1）检索能力对外部数据源与认证策略存在依赖：OpenAlex 官方已调整访问策略、要求配置 API Key，未配置密钥时真实检索无法进行，系统可用性受第三方服务策略变化影响（ISSUE-003）；

（2）评测样本规模有限：文献相关性金标准目前仅含 6 篇相关与 6 篇不相关的人工标注论文，覆盖课题面较窄，当前 F1=1.0 的结果仍需在更大样本上进一步验证（ISSUE-008）；

（3）本地模型算力与上下文约束明显：采用 14B 级本地模型进行语义筛选时，单课题端到端流程一度耗时 286.3 s，经检索策略与评分流程优化后降至 141.0 s，但长文档处理仍受上下文窗口限制需分片，整体吞吐与硬件配置强相关（ISSUE-002）；

（4）对上游依赖演进较敏感：FastAPI 测试客户端、FastMCP/Authlib 等组件曾出现上游弃用警告，需要持续跟踪依赖升级与回归测试以维持长期稳定（ISSUE-004/005）。
